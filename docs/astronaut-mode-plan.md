# Astronaut Mode implementation plan

Planning only: no authentication, production database connection, environment change, account creation or cloud import was implemented in this step. Explore Demo continues to work without credentials.

## Proposed sequence

1. **Make the mode explicit.** Add a typed demo versus authenticated session context with separate repository factories, caches, chat namespaces and navigation. Explore Demo retains fictional labels and scenarios. Astronaut Mode starts with an empty history and a friendly first-check-in action; it must never copy, seed, merge or silently upload demo rows.
2. **Add authentication after approval.** Follow the current [Supabase Next.js SSR guidance](https://supabase.com/docs/guides/auth/server-side/nextjs), using separate browser/server clients and supported session-cookie refresh. Implement sign-in, callback/error and logout flows. Verify identity server-side rather than trusting an unverified session object or client-provided profile ID. Keep privileged keys out of browser code and ordinary user-record operations. No secrets should be pasted into chat.
3. **Create the owned profile.** Link the profile to the verified Auth user, with explicit onboarding and one-profile ownership semantics. Review the prepared schema against [Supabase user-data guidance](https://supabase.com/docs/guides/auth/managing-user-data). Derive the active profile on the server; a selected UUID alone grants no access.
4. **Harden persistence before connecting it.** Review migrations, foreign keys, idempotent submission IDs, timestamps and cross-user ownership tests. Enforce RLS for reads and writes, with no anonymous private-record access or service-role bypass. Follow [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security). Append a new migration for the SpO₂ write rule (nullable, 1–100), rather than rewriting the historical migration that allowed zero. Inventory and visibly flag any existing zeros first; preserve originals and audit any explicit authorized correction. Do not auto-convert or delete ambiguous historical values. Regenerate types only after approved schema changes.
5. **Connect private check-ins/history.** Use the verified-user repository behind authenticated handlers. Return clear loading, empty, save-error and signed-out states. Retry by stable submission ID; confirm persistence rather than claiming a save on network failure. Protect private responses from shared caching. Test cross-device retrieval under the same user; ensure another user cannot read or mutate the rows. Cloud failure must not substitute fictional history.
6. **Isolate account transitions and analysis.** Key providers/caches by mode and verified owner. Abort and invalidate in-flight reads on logout/account switch; discard late responses and remove private state from memory. Preserve the separate demo database. Recompute insights only from that user's records. Authenticated assistant access needs a new reviewed server authorization/consent path; do not extend the current public demo enum into a private-record lookup.

## Release gates

- Use a disposable development Supabase project/stack only after explicit approval. Configure reviewed redirect URLs and approved environment variables separately; do not modify current production settings as part of this plan.
- Verify anonymous denial, owner-only insert/read/update/delete, forged IDs, ownership transfer attempts, two-user/account switching, logout/back navigation, token expiry, refresh, retry idempotency, cross-device history, nullable/invalid SpO₂ and empty personal histories. Execute actual SQL/RLS tests; mocked/static checks do not establish RLS correctness.
- Demonstrate that demo scenario A/B/C selection cannot overwrite personal or local demo history, and that no demo record is imported into a new account.
- Review data retention, access logging, correction/export/deletion, consent and clinical/privacy obligations before collecting real medical information. Authentication and RLS alone do not establish clinical suitability or compliance.

Official documentation was consulted for this plan; its implementation details should be rechecked when that future step begins. No live Supabase behavior is claimed verified here.
